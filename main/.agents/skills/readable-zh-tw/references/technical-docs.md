# 技術文檔：寫給工程師看的中文

這一份是 `readable-zh-tw` 直出模式的延伸，對象是專案 README、`docs/*.md`、skill、設計說明與
程式碼註解裡的中文敘述。[SKILL.md](../SKILL.md) 的直出規則全部照用，這裡只寫技術文檔多出來
的部分。SKILL.md frontmatter 的不觸發清單寫著「程式碼」，那指的是程式碼本身，不要去改；註解
與 JSDoc 裡的中文是寫給人讀的散文，適用。

其他 reference 都是從上游蒸餾的，這一份不是——上游處理的是電子報與貼文，技術文檔不在它的
範圍內，所以下面六條是本專案自己觀察到的（前四條 2026-08-26，第 5、6 條 2026-09-03）。

技術文檔會往兩個相反的方向壞掉：**減廢話減過頭，把事實一起減掉**；或者**壓縮過頭，變成讀者
要解碼的密碼**。第 1 條防前者，第 4 條防後者，中間兩條是技術文檔特有的兩種雜訊。第 5、6 條
處理的是另一個問題：這些規則落到別人的專案、落到程式碼註解上時，怎麼判。

## 1. 減廢話停在規格值上

數字、路徑、識別字、指令、參數、量測結果照原樣保留，只改包在外面的敘述。「大約兩千字」不能
取代 `1935`，「跑一下測試」不能取代那一行指令。

拿不準一個 token 算不算規格值時，問它：**換一個寫法之後，讀者還能不能用它重跑同一件事？**
不能就是規格值。

改稿模式有完整的[保護清單](protected-list.md)，直出沒有，因為交出去的東西是自己寫的。這一條
就是直出唯一需要的等價物。

## 2. 表格說完就不要再用散文說一次

技術文檔最常見的重複不是贅詞，是一張表格加底下一段把同樣內容再講一遍。留一個就好：要對照就
留表格，表格怎麼排見 SKILL.md 的〈版面服務掃讀〉；只有一兩項就刪掉表格，留散文。

同一件事在同一份文件裡講兩次，讀者要多花力氣確認那兩次是不是真的一樣——那才是重複真正的
成本，不是多出來的字數。

## 3. 量測與除錯的敘述不做戲劇化鋪陳

「看起來像鐵證」「差點就判成 X」「這才證明」這類鋪陳在報告裡是雜訊。讀者要的是兩件事：量到
什麼、據此判斷什麼。

❌ 這個數字看起來像鐵證，直到重跑才發現基準是錯的——這才證明第一輪什麼都沒測到。
✅ 第一輪的基準錯了（比對對象不是實際來源），重跑後六個檔案全部相同。

這是 [patterns.md](patterns.md) 第 20 條「人工戲劇」在技術文檔裡的樣子：那裡演的是情緒，這裡
演的是推理過程的驚險。

誤殺邊界：排除順序本身是資訊。「先排除 A，因為 B」該留；判準是拿掉那一句之後，結論還站不
站得住。

## 4. 另一端：不要壓成要解碼的密碼

壓縮過頭的樣子是等式式縮寫（`常駐面＝每 session 必載`）、四字格連發，以及連續名詞堆疊
（「派工結果品質檢查失敗率」）。字數少了，但讀者得逐句解碼，總時間更長。

落點是**中性說明文**：淺白到不用解碼，但不是把話講成口頭解釋。等式換回一個句子，名詞串拆成
一個有動詞的句子（「品質檢查判失敗的派工佔多少」），四字格只在它本來就是既有術語時才用。

這一條和 SKILL.md 的〈術語可及性〉是同一個目標的兩面：那裡管一個術語第一次出現的樣子，這裡
管句子的密度。

## 5. 專案既有慣例優先於通則

要動用語或標點之前，先量專案裡兩種寫法各有幾個（`grep -rc` 就夠）。既有慣例佔多數就不改，
並在回報裡寫明為什麼不改。在一份文件裡製造不一致，比留著一個不那麼標準的寫法更難讀。

這一條管的是**風格選擇**：標點形式、不在替換表上的近義詞。
[taiwan-localization.md](taiwan-localization.md) 的替換表是硬規則，量測不豁免它——量到的多數
只決定改法（整份一起改，或先回報再改），不決定改不改。

SKILL.md〈半形標點與台灣用語〉的半形就是這種風格選擇，而且它是**本 harness 回覆**的慣例。
文字要落進別的 repo 的檔案時，以那個 repo 量到的慣例為準。

## 6. 程式碼註解與 JSDoc

註解的讀法和 markdown 不一樣：IDE 上一次只浮出一個宣告，沒有標題與列表可以靠，所以每一則都
要能單獨讀懂。兩條就夠了。

1. **寫呼叫端要據以做決定的事實**：預設值、生命週期、清理責任、錯誤行為、座標與單位。
2. **機制只在它會改變呼叫方式時才寫。**「內部為什麼這樣運作」不是呼叫端的決策依據，括號補述
   最容易變成這種東西。

❌ 未啟用的 feature chunk 永遠不會被請求（`React.lazy` 要等元件真的被 render 才呼叫 loader）
✅ 沒被渲染的 chunk 不會被請求

第 1 條防的是把事實減掉，第 4 條防的是壓成密碼，這一條防的是第三種：每一句都對，但講的是呼叫
端不需要知道的那一半，讀者得自己挑出哪一句跟他有關。

## 交出前的檢查

- [ ] 每個數字、路徑、指令都還是原本那一個？
- [ ] 有沒有一段散文在重述上面那張表？
- [ ] 有沒有哪一句在替量測結果做鋪陳？
- [ ] 有沒有哪一句要讀兩次才知道在說什麼？
- [ ] 改用語或標點之前，量過專案裡的既有寫法嗎？
- [ ] 從頭讀一遍成品，第一個需要往回翻的地方在哪裡？

最後一項是唯一的整體檢查。前面五項都是局部的，順序錯了一項都不會亮：定義補在文末、限制寫在
讀者還不知道那是什麼的時候，每一句拆開看都沒問題。
