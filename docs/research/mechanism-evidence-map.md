## 盤點方法, 以及它第一次就騙了我

列舉是機械的:

```
hook        ls main/claude/hooks/*.py                       11
git hook    main/claude/githooks/pre-commit                  1
skill       main/{claude,codex,.agents}/skills/*/ 去重       10   (+2 repo-root dev-only)
script      ls scripts/*.{py,sh}                            21
script      main/{claude,codex,.agents}/scripts/ 去重        11   (部署到 HOME)
role        ls main/claude/agents/*.md (雙生算一組)            7
eval        evals/replay/scenarios/ 47 + evals/traps/ 5      52
                                                           ----
                                                            115
```

**第一版的探針報錯了.** 我先用「docs 裡提到幾次這個機制的名字」當依據強度, 結果
`codename-gloss-report` 命中 0, 讀起來像一支沒有人要的腳本. 打開它才發現它的 docstring 第三行
就寫著 `docs/README.md` 規則 8 —— **依據記在程式碼裡, 方向和我的探針相反**. 一次改掃全檔加上
反向 (script → doc), 那 0 變成 1.

這值得留著, 因為它就是本 repo 反覆記的那個形狀: 探針的沉默讀起來和「真的沒有」一模一樣.
下面每一個「0」都經過反向複查, 但**只複查了 script 與 hook 兩類**, skill 與 role 那兩類沒有反向掃.

## 三個缺口, 都是量到的

### 缺口一: 證據厚的地方和機制厚的地方幾乎不重疊

`evals/` 底下 52 個情境, 累計 463+ 個 replay run, 沒有一個是**關於某個 gate 會不會擋**的.
全 repo grep 七個 gate 名字, `evals/` 只命中三處, 而且都不是情境: `lifecycle-criteria.py` (判準),
`surface.tsv` (量測面指紋), 和一個 run 的 `replies.md` (偶然提及).

五個 trap 量的是 false completion, spec conflict, tz bucketing, skill recall, pointer redundancy ——
全部是契約與 skill 的行為. 47 個 replay 情境量的是派工成本, 措辭效應, 語言子句, 注入位置.

**數字要精確**: 真的攔得住東西的是 **7 個 fail-closed gate** (`commit-test-gate`, `push-consent-gate`, `leaf-redispatch`, `runtime-guard --gate`, `verifier-quota`, `managed-target-guard`, `githooks/pre-commit`), 另外 5 支是 fail-open 只記錄. **12 是 hook 數不是 gate 數**, 而下面 M1 與 M5 的對象是那 7 個 —— fail-open 的 5 支沒有命中數也沒有停止條件可寫.

**所以我們的知識庫是關於「模型會不會照契約做」的, 而我們的機制有一半是「模型做了會不會被擋住」.**
後者目前只由單元測試與合成 pipe-test 支撐 —— 那證明的是**程式邏輯對**, 不是**放在真實 session
裡有用**. `hook-system.md` 的三關驗證誠實地只宣稱前者.

這不是說 gate 沒有價值: `denials.jsonl` 有 28 筆真實攔截, 那是「它真的擋過」的直接證據.
缺的是「擋了之後結果比較好」, 而那正是[研究摘要驗證缺口](README.md#驗證缺口)第五條
(「從來沒有量過規則觸發了有沒有比較好」) 在契約層講的同一件事, 只是沒有人在 gate 層講過.

**這一格是本次盤點最值錢的發現**, 而且它剛好和 [ECC 計畫 Q3](ecc-survey.md#升級計畫-結案表與重開條件)
撞在一起 —— fact-forcing 的第一階段 (只記錄不攔) 產生的就是 gate 層的第一批行為資料.

### 缺口二: 儀器跑得動, 但多數沒有排程讀者

**2026-09-08 分檔**: `test_mechanisms.py` 當天到 150/462 (32.5%, 天花板 33%), 而報這件事的守衛明寫「split at a seam, do not raise the constant」. 縫是**這個東西做什麼**: `test_mechanisms` 留下閘, 派工, trap 與表面 —— 會擋, 會路由, 會記錄的; 新的 `test_reporters.py` 拿走十個只算一個數字然後印出來的工具. 它們全部設計成 exit 0, 而那正是它們的測試該放在一起的理由: 對報表而言「它跑起來了」不是被測的性質. 分完 25.1%.

21 支 repo script 全部被套件引用, 抽查的多數確實被 `load_module` 或 subprocess 跑過 —— 但**不是 21/21**: `docs-size-report.py` 在整個 `main/claude/tests/` 底下只出現一次, 是 `test_contracts.py:1809` 的一行註解, 而 githooks 與 `sync.sh` 也不呼叫它. 它是唯一一支既沒有排程讀者也沒有自動執行者的報表, 所以它是 M2 候刪清單的第一個名字.
但「被套件跑過」和「有人讀它的輸出」是兩件事, 而**自動被讀**的只有: `contract-operator-delta` (git pre-commit 對暫存的 prompt-surface 檔印),
`sync.sh` / `merge-settings` / `merge-toml` (部署路徑), 以及 `weekly-integrity` 讀的三支部署 script.
其餘 17 支要有人記得跑.

**2026-09-08 量到並處理 (M2)**: 21 支裡有排程讀者的是 5 支 (`contract-operator-delta` 走 githook; `install-git-hooks`, `merge-settings`, `sync.sh` 走部署路徑; `merge-toml` 走 weekly). 其中只有 `contract-operator-delta` 是報表 —— 14 支報表裡 13 支沒有排程讀者. 處置不是把 13 支排進 `weekly-integrity`, 而是每支宣告自己的**觸發事件**; 候刪清單是空的.

`hook-system.md` 已經記過這個教訓的一次犯案 (「沒人讀的儀器不會告訴你它壞了」, 2026-08-20,
35,856 列裡只有 3 列是真的). 那次修的是**寫入端**; 讀取端到今天仍然是人力.

不主張把 17 支都塞進 `weekly-integrity` —— 那會把一份每週報告變成沒有人看完的長清單, 是同一個
失敗的另一種形狀. 主張的是**每支報表宣告自己該多久被讀一次**, 沒有答案的那幾支就是候刪.

### 缺口三: 依據的方向是單向的

程式碼指得到文件 (10/21 支 script 引用了 `docs/` 路徑; **09-08 更正**: 另外 10 支也解釋了自己, 只是指向姊妹腳本, 測試與事故日期, 所以「有依據」的真實比例是 20/21, 而 10/21 量的是引用形式不是依據有無), 文件指不回程式碼. 後果具體: 從證據那一側**列舉不出
「這份研究產生了什麼機制」**, 所以一份研究結論被推翻時, 沒有機械的方法找出哪些機制建在它上面.

現存的三份綜合文件都在證據那一側, 這就是為什麼它們答不了使用者這次問的後半句.

## 補讀之後的三條重新結論

初稿是先列舉機制再讀語料. 補讀六份研究文的結論段之後, 有三條要改, 兩條是降級.

### 一, M1 不是「fact-forcing 的前置」, 它就是主體 —— 而 fact-forcing 本身該降級

`trap-experiments` 的合計是 **37 個有效樣本, 實質陷阱 0 中招**; 失敗全部集中在格式 (強制行),
而每一種都被一句對症的措辭關掉. `landing-readiness` 的發現五據此寫下「再往實質防線加規則,
沒有證據支持」.

[ECC 計畫 Q3](ecc-survey.md#升級計畫-結案表與重開條件) 的 fact-forcing **正是往實質防線加規則**.
兩者放在一起, 正確的讀法不是「所以不要做」, 而是:

```text
37 個 run 說   實質防線目前沒有可觀察的失效        →  加規則沒有依據
缺口一說       gate 層完全沒有行為資料             →  「沒有失效」也可能是沒在看
                                                    ↓
              先量現有那 7 個, 而不是先加第 8 個
```

**所以 M1 與 Q3 第一階段合併**, 且主體是 M1 (量現有 7 個 fail-closed gate 的真實命中), 不是 Q3
(為新守衛鋪路). 兩件事的差別在於: 如果兩週的資料顯示那 7 個幾乎不攔, 那麼 fact-forcing
連問題都沒有; 如果顯示常攔, 那麼**該修的是常攔的那幾支**, 而不是再加一支.

**這改變了 [ECC 計畫](ecc-survey.md#升級計畫-結案表與重開條件)的排序**: Q3 從「最有價值但風險最高,
所以排最後」變成「依據被語料削弱, 併入 M1 之後才重新評估」.

### 二, 缺口二 (儀器沒有排程讀者) 的嚴重度下修, 因為尺度論證擋在前面

`resident-context-options` 的核心讀數是常駐字數只佔真實 prompt 的 **0.049% (p50)**, 而它的
「六分之一」那一節更進一步: 一個 session 收到的 skill 描述有 **79.4%** 不是本 repo 出貨的,
完全不在任何棘輪內, 而那一節明白寫了**不做成閘**的理由 (不是這一層付的成本, 就只報不擋).

同一條判準套到報表上: 17 支沒有排程讀者的報表, **它們的成本是人的注意力而不是模型的 context**.
所以 M2 (宣告讀取節奏) 的價值是**篩掉不該存在的報表**, 不是「讓更多報表被讀」——
把 17 支都排進 `weekly-integrity` 會製造一份沒有人看完的長清單, 那是同一個失敗的另一種形狀.
M2 的完成條件因此改成: **至少判定一支候刪**, 而不是「21 支都有宣告」.

### 三, 「量到的東西逐條不同」這一條, 讓本文的主表不能被讀成評分

`clause-pricing` 的 `m1` 量到一句話換掉觸發率三倍 (14/92 → 44/91, p = 0.0000014), 而
`wording-effect-scale` 用 30 個 run 證明那把尺**無法外推**到別的子句. 兩份合起來的一句話是:
**每條子句的效應要各自量, 量過的那條算數, 沒量過的不要借.**

本文主表列了「幾份文件提到這個機制」與「有沒有引用它服務的文件」. 那兩欄量的是**可發現性**,
不是效力. 一個被 21 份文件提到的機制 (`baton-dispatch`) 不因此比被 4 份提到的
(`test-first-change`) 更有依據 —— 前者只是被討論得多. **主表不是評分表**, 而初稿沒有把這句寫死,
現在寫在這裡.

## M1 的基線, 以及它推翻了自己的決策規則 (2026-09-08)

M1 想要「gate 層的第一批行為資料」. 開始建之前先查現況, 而現況是**儀器早就在**:
`denials.jsonl` 從 2026-08-19 起逐筆記著每一次攔截, `denial-report.py` 已經按閘, 理由與日期
彙總. 所以 M1 不是造一支記錄器, 是**讀一次現有的資料, 並且先把讀法釘死**.

### 先跑正控制, 因為這是缺席宣稱

`verifier-quota` 與 `runtime-guard` 的計數是 0. 那讀起來和「它們從不記錄」一模一樣, 而後者
更可能 —— 文件自己寫的是「**六個** gate 會留下拒絕紀錄」而閘有七個. 所以先逼它們各攔一次:

```text
leaf-redispatch      exit 2   落列 ✓   (已知會攔, 這一臂是在校準探針本身)
verifier-quota #1    exit 0   不攔     (額度是 1, 第一個本來就該過)
verifier-quota #2    exit 2   落列 ✓
runtime-guard --gate exit 2   落列 ✓
```

**探針第一次跑是錯的, 兩次**: `verifier-quota` 的 payload 少了 `prompt_id` (它自己在 stderr
說了, 而且明說沒有 id 就不執行額度), `runtime-guard` 的版本我用環境變數餵 —— 但
`AGENT_RUNTIME_VERSION` 是 `weekly-integrity` 讀的, 這一支要的是命令列參數. 兩次都是儀器錯
不是系統錯, 而如果沒跑正控制, 兩個 exit 0 會被我讀成「這兩個閘從不觸發」.

正控制過了, 所以下面那兩個 0 是**真的缺席**.

### 基線 (2026-08-20 至 09-08, 20 天)

排除 2026-08-20 之前的 3 列 —— 那段期間套件的 fixture 攔截與真實攔截共用同一份紀錄.

| 閘 | 攔截次數 | 註 |
|---|---:|---|
| commit-test-gate | 25 | **Bash 側與 git 側分不開**: 25 列全部沒有 `session_id`, 而那正是 git 側拿不到 payload 的特徵 |
| managed-target-guard | 2 | |
| push-consent-gate | 2 | 它 09-06 才從提醒升成閘 |
| leaf-redispatch | 1 | |
| runtime-guard | 0 | 正控制證明它會記錄 |
| verifier-quota | 0 | 同上 |

**七個閘裡有四個在二十天內攔了不到三次, 兩個一次都沒有.**

### 而 M1 原本寫的決策規則是無效的

原文寫: 「幾乎不攔 → fact-forcing 連問題都沒有; 常攔 → 該修的是常攔的那幾支」.

**前半推不出來.** 現有七個閘守的是 commit 的測試狀態, push 的同意, 派工深度, verifier 額度,
CLI 版本, 與部署輸出. **沒有一個守 fact-forcing 要守的那個面** —— 每檔第一次編輯前有沒有先
調查. 拿 A 的閒置去論證 B 不需要, 是拿一把量不到那件事的尺去宣告那件事不存在.

這是我自己在 09-08 早先寫進計畫的規則, 而它撐不住. 兩件事因此要分開:

- **M1 (本節) 已完成**: 現有閘的行為基線, 帶校準.
- **Q3 第一階段仍然是獨立的一項**: 它要的是「每檔第一次寫入」的計數, 而**現在沒有任何東西
  在數那個**. 先前把兩者合併是錯的, 合併的理由 (「先量再加閘」) 仍然成立, 但要量的是兩份
  不同的資料.

### 這批基線能與不能 licence 什麼

- **可以說**: 這台機器上, 二十天內, 守派工安全的兩個閘 (`leaf-redispatch`, `verifier-quota`)
  合計攔了 1 次; 攔截量集中在 commit 的測試狀態.
- **不可以說**: 攔得少的閘沒有用. 一個從不觸發的閘可能是在**嚇阻** —— 契約同時也叫模型別做
  那件事, 所以 0 可能是契約在生效而不是閘閒置. 要分開這兩者, 得有一個「契約沒講但閘還在」
  的臂, 那是 replay 的構造不是紀錄的構造.
- **不可以說**: 這代表一般情況. 一台機器, 一個使用者, 二十天, 而其中 `push-consent-gate`
  只有兩天是閘.

**推翻條件**: 任何一個現在讀 0 的閘在下次讀取 (`denial-report.py` 宣告的節奏是每月) 出現
非零, 這一節的「四個攔不到三次」要重寫; 而若 `commit-test-gate` 的 25 次能被拆成兩側,
那一列要分開記 —— 現在分不開是因為 git 側沒有 payload, 不是因為沒人想分.

### 連續兩項的資料早就在, 而我差點兩次都去造儀器

**這些數字的分母會長.** transcript 語料是活的 —— 重跑同一支探針, Skill 呼叫從 144 變 145,
因為量完之後又發生了一次. 所以這一節的每個計數都是 **2026-09-08 當天的讀數**, 而重跑時
分母偏大是正常的, 不是先前記錯. 會失效的是**比例**, 不是絕對數: 若 Skill 失敗率從 0.7%
升到 3%, 那才是推翻條件.


M1 要「gate 層的行為資料」, 而 `denials.jsonl` 已經記了二十天. Q6 要「哪支 skill 常失敗」,
而 286 份 transcript 已經記著每一次 `tool_use` 與它的 `tool_result` —— 配對一次就得到
Skill 144 次呼叫 1 次失敗, 連那一次都不是目標訊號.

兩次都是同一個順序錯誤: **先設計記錄器, 才問「現在有什麼在記」**. 代價不只是白做,
而是每多一份遙測就多一份沒人讀的檔案 —— 那正是這個 repo 2026-08-20 付過的學費.

所以剩下的項目各加一個前置問題: **這件事現在有什麼在記, 而它為什麼不夠**.
Q3 的記錄器過得了這一關 (沒有任何東西在數「每檔第一次寫入」, M1 那一節已經確認),
但它得自己說出來, 不能預設.

## Q3 的前置問題也答完了: 語料早就記著, 而閘要擋的事已經在發生 (2026-09-08)

Q6 之後給剩下每一項加的前置問題是「這件事現在有什麼在記」. Q3 的記錄器本來是唯一被判定
「沒有東西在記」的一項 —— 而那個判定是錯的. Transcript 記著每一次 `Edit` 的 `file_path`,
所以「每檔第一次寫入」本來就數得出來.

### 儀器錯了一次, 而它錯得很明顯

第一版只認 `Read`/`Grep`/`Glob` 三個工具, 讀出「三分之一的首次 Edit 沒讀過就改」. 那不可能:
**client 本身就拒絕沒在對話裡讀過的檔案的 Edit**. 而解釋就在這個 repo 自己的 auto mode ——
它叫助理用 `cat`, `sed -n`, `head` 讀檔, 那些是 Bash, 工具名探針看不見.

解析 shell 去判斷是這個 repo 明文不做的事, 所以改成**夾出區間**而不是挑一個寬鬆定義:

| | 判準 | 首次 Edit 665 次 |
|---|---|---:|
| 下界 | 用 `Read`/`Grep`/`Glob` 讀過這個檔 | 390 (58.6%) |
| | 之前有 Bash 指令提到這個檔名 | 229 (34.4%) |
| 上界 | 兩者皆無 | **46 (6.9%)** |

**先調查過的比例落在 59% 到 93% 之間.** 一個包得住答案的區間, 勝過一個自信而錯誤的點估計.

### 所以 Q3 不做, 而理由比原本的強得多

fact-forcing 要擋的是「沒調查就編輯」. 這個語料裡那件事最多發生在 **6.9% 的首次 Edit**,
而且那 6.9% 是**上界** —— 檔案還可能以這兩支探針都看不見的方式被看過 (在 subagent 裡讀,
或在 diff 裡看到).

更關鍵的是**下限那一半已經是機械強制的**: client 拒絕沒讀過就 Edit. 加一道閘去擋一件
client 已經在擋的事, 買到的是第二次拒絕而不是第一次.

### 這個量測不能宣稱的

ECC 的閘要的**不只是「讀過這個檔」**, 它要 importer 清單, 受影響的公開 API, 資料 schema.
上面量的是「這個檔有沒有被看過」, 不是「有沒有列出 importer」. 所以撐得住的是
**那道閘的前提大多已經滿足**; 撐不住的是「更深的調查也已經在做」—— 那沒有量.

**推翻條件**: 「兩者皆無」的比例在下次量到超過 20%, 或出現一次可歸因於「沒調查就改」的
實質缺陷 (`trap-experiments` 至今 37/37 沒有). 重量的方法是那支夾擊掃描, 成本一次執行.

## Q3b: 破壞性指令的誤報率會先殺掉那道閘 (2026-09-08)

同樣先問語料. Transcript 記著 **18,812 次 Bash 呼叫**, 所以「那道閘會攔幾次」數得出來.
樣式用 ECC 自己的破壞性集合 (`gateguard-fact-force.js`), 不是我發明的.

校準: `git commit` 891 次, `git push` 44 次 —— 兩個已知會發生且已知有閘的都非零, 掃描器不瞎.

### 它會攔什麼

| 樣式 | 命中 | 佔 Bash |
|---|---:|---:|
| `rm -rf` | 368 | 1.96% |
| `rm` (任何) | 429 | 2.28% |
| `>` 重導 | 5,043 | 26.81% |
| `mv` 覆蓋 | 84 | 0.45% |
| `git checkout --` | 55 | 0.29% |
| `git reset --hard` | 26 | 0.14% |
| `truncate` / `dd if=` | 11 | 0.06% |
| SQL `drop`/`delete`, `chmod -R` | 0 | 0 |

`>` 一項就佔四分之一的 Bash 呼叫. 一道在四分之一的指令上停下來的閘, 不是守衛, 是勸人關掉它的邀請函.

### 誤報率量過了, 而它是決定性的

把 374 個 `rm -rf`/`rm -f` 依目標分類:

| 目標 | 數 | 佔比 |
|---|---:|---:|
| 暫存區或 `/tmp` | 212 | 56.7% |
| 建置產物 (`node_modules`, `__pycache__`, `dist`) | 50 | 13.4% |
| 其他相對路徑 | 107 | 28.6% |
| HOME 或絕對路徑 | 5 | 1.3% |

**至少 70% 是清理自己產生的東西**, 而那 107 個相對路徑的樣本讀起來也是刻意的工作
(刪掉 smoke test 的 run 目錄, 換掉正在重寫的來源檔).

那 5 個絕對路徑逐一看過: `.trap-runs`, `__probe_rules.html`, 一個生成出來的 `projects` 目錄 ——
**全部在專案工作區內, 沒有一個碰到 `~/.claude`, `~/.codex` 或 `~/.agents`**.

**所以不做.** 本 repo 自己的規則寫著「守衛帶著沒量過的誤報率, 是一份請大家忽略這個測試的提案」;
這裡量過了, 而且是 70% 起跳, 對照的是 18,812 次呼叫裡 **0 次可觀察的傷害**.

### 但有一個真的洞, 值得指名

`managed-target-guard` 看的是 `Write`/`Edit`/`NotebookEdit`. **它看不到 Bash.**
所以 `rm -rf ~/.claude/hooks` 這種指令現在沒有任何機制擋 —— 那是託管狀態, 而刪除路徑是敞開的.

**它從來沒有發生過** (18,812 次呼叫, 0 次), 所以現在不加閘; 沒有資料就加閘正是這一輪
反覆拒絕的事. 但這個洞是真的, 寫在這裡以免下次有人以為託管邊界是完整的.

**推翻條件**: 出現任何一次 Bash 刪除或覆寫 `~/.claude`, `~/.codex`, `~/.agents` 底下的
託管檔案. 一次就夠 —— 那時要加的不是 fact-forcing, 是把 `managed-target-guard` 的判斷
接到 Bash 側, 而那是一個窄得多的閘.

## Q8: 威脅形狀存在, 而那正是為什麼那條規則不能是毯子 (2026-09-08)

前四項的量測都以「這件事沒發生過」收尾. 這一項不是, 而結論反而更硬.

### 「不可信 run」的定義先寫成可判定的

規則要成立, 「不可信」得是 hook 評估得了的東西, 不是一句形容. 定義: **這個 session 抓過
repo 沒有寫的內容** —— WebFetch, WebSearch, 瀏覽器工具, 或 Bash 裡的 `git clone`/`git fetch`/
`curl`/`wget`. 校準: 這個 session 自己 clone 了一個第三方 repo, 所以至少要有一個落進去.

### 量到的

| | 有寫 memory | 沒寫 memory |
|---|---:|---:|
| **抓過外部內容** | **23 (8.0%)** | 17 (5.9%) |
| 沒抓 | 3 (1.0%) | 243 (85.0%) |

286 個 session, 40 個抓過 (校準通過).

**26 個寫過 memory 的 session 裡, 23 個也抓過外部內容 —— 88%.**

### 所以毯子版不做

「不可信 run 之後 memory 要另外標記或不寫」會在 **88% 的 memory 寫入上觸發**. 一條在幾乎每次
都觸發的規則不是篩子, 是毯子; 它和 Q3b 的 `>` 佔 26.8% 是同一個形狀, 只是更極端.

**而真正能分辨的問題是「這則 memory 是不是關於抓進來的東西」—— 那是判斷, 不是機械判定**,
所以它不能是 hook. 本 repo 的分工寫得很清楚: 需要判斷的交給模型, 能機械判定的交給 hook.

### 現存的 memory 逐則看過, 沒有一則來自抓進來的內容

四則全部是關於這個 repo 自己的工作方式 —— 文件風格, push 授權, 當場觀察狀態, 派工紀錄的兩個
時期. 威脅形狀在 (88% 共現), 但**實現的風險目前是零**.

### 剩下的是寫作紀律, 不是機制

有用的那條會是: **一則 memory 的內容若來自抓進來的材料, 要指名它從哪來**. 而 memory schema
的 `reference` 型別本來就是「指向外部資源的指標」—— 那條紀律有一半已經在了.

**這一段沒有落地, 而且不該由我落地**: 那句話要進的是使用者的 memory 契約, 那是他的 prompt
表面. 記在這裡, 決定權在他.

**順帶一個 schema 觀察**: 現存四則的 frontmatter 都寫 `type: memory`, 而契約宣告的集合是
`user | feedback | project | reference`. 四則都用了集合外的值. 那是 memory 契約自己的
一致性問題, 與 Q8 無關, 也沒有動 —— 那是使用者的檔案.

**推翻條件**: 出現一則 memory, 其內容可追溯到某次抓進來的材料. 那時要加的是寫作紀律的那一句,
而不是毯子規則.
