# 用產出品質給常駐子句定價

從 [lifecycle-replay.md](lifecycle-replay.md) 分出來的一條線, 因為它問的是一個
獨立的問題: **一條常駐契約子句, 能不能用「使用者拿到的東西好不好」來定價**, 而
不是用「規則有沒有照自己的話執行」. 分出來的直接原因是 sprawl guard —— 那道閘的
用意就是「一份文件長過單一職責就拆掉, 不要調高常數」.

判準要同時滿足三件事, 少一件就不算:

```text
1  評分對象是產出本身, 不是標記有沒有出現
2  第三方能從留存 artifact 重算 (判準 4) —— 跑的人自己說「有做到」不算
3  子句要有作用空間 —— 不在天花板也不在地板
```

四格的結論, 依序: `q1` 與 `q2` 證明產出正確性在**結構上**給不了隔離類子句分數;
`v1` 與 `v2` 把同一個判準架在一條做加法的子句上, 判準跑得起來, 而 fixture 的陷阱
落在閱讀距離之內.

存活判準本身, 以及中斷恢復 / 連續 correction / 衝突 leaf 那三個生命週期問題, 仍然
在 [lifecycle-replay.md](lifecycle-replay.md).

## 結果品質的判準 — 2026-08-15 事前登記, 尚未開跑

本目錄量到今天為止的東西全部是**行為**: 規則有沒有觸發, skill 有沒有載入, 標記有沒有出現. 沒有一格量過「觸發了有沒有比較好」. `d1` 三臂 5/5 全載入 `baton-dispatch`, 而**沒有人檢查三臂派回來的東西品質是否相同** — 契約子句刪掉後若載入照舊但品質下降, 現行量測面完全看不見. 要能拿量測結果去刪常駐子句, 缺的就是這一格.

**為什麼不直接沿用 `r3`.** 因為量過了: `r3` 的判準 (兩份 leaf 的 clause token 都活著抵達結論) 在 arm A 拿 **5/5**. 一個貼在天花板的判準沒辦法顯示任何子句值多少錢, 因為沒有可掉的空間. 這不是推測, 是 2026-08-13 那批的數字.

**`q1-clause-verdicts` 改量哪一件事.** 保留 `r3` 的程式碼 (逐位元組相同) 與逐字相同的 turn 1, 把兩份權威文件加厚成各自帶 id 的條款, 十一條, 每一條事前寫死一個裁決:

```text
兩份文件共 11 條   PASS 5   VIOLATED 4   CONFLICT 2
其中 9 條          單看一份文件 + 程式碼就能判
其中 2 條          只有把兩份 leaf 報告並排才判得出來 (3 次 vs 至少 5 次)
```

那兩條是關鍵: **任何一個隔離的 reviewer 都不可能標得出來**, 因為它看不到對面那份文件. 分數因此讀的是派工, 不是模型.

三個「近似陷阱」是故意的, 用來把「聞到味道」和「對著條文判」分開:

- `BACKOFF_MS = 250` 宣告了從沒用過 → 對 policy 的「backoff 由實作裁量」是 **PASS**, 對 runbook 的「間隔至少 200 ms」是 **VIOLATED**. 同一個程式事實, 兩個相反的正確答案.
- `except TimeoutError` 只攔逾時 → 是個味道, 但 policy 有一條**指名允許**它, 所以 **PASS**.
- 全部答同一個字最高只有 5/11, 所以「一律 PASS」這種退化策略拿不到分.

**turn 2 不准回頭翻檔案, 也不准再派人**, 從 tool stream 檢查而不是靠自述. 回頭翻了的 run 回答的是「模型會不會判」而不是「派工帶回來的夠不夠判」, 那是 invalid 而非 incorrect — 判準 2 的老規矩, 用在新格上.

### 開跑前先寫死的三條規則

1. **天花板閘 (先跑 arm A, n=5).** arm A 的 `label_score` 平均 ≥ 10/11 就宣告這個判準也貼到天花板, **不跑 B/C**, 記錄下來重新設計. 這一條存在的理由就是 `r3` 的 5/5 — 同一個錯誤不付兩次錢.
2. **地板閘.** arm A 平均 ≤ 6/11 (退化策略是 5/11) 代表量到的是題目的歧義不是答題的品質, 一樣不跑 B/C.
3. **條目退場規則.** arm A 五個 run 裡有 ≥3 個對同一條給出**同一個**與答案不符的標籤, 推定是答案鍵編碼了寫題者的意見, 該條**在比臂之前退場**, 三臂一律不計. 只准用 arm A 的資料判, 且只准在比臂之前判一次.

### 事前寫死的比臂判準

n=5/臂, 單位是 run 不是條目 (同一個 run 的十一條不獨立):

| 讀法 | 條件 |
|---|---|
| **可以刪** | arm C 平均 ≥ arm A 平均 − 1.0 條, 且 arm C 最差的 run 不低於 arm A 最差的 run 2 條以上 |
| **要保留** | arm A 平均 ≥ arm C 平均 + 2.0 條 |
| **無定論** | 其餘一切 |

**n=5 分不出小於約 2 條的差距**, 這句話先寫在這裡, 免得事後拿一個 0.4 條的差當結論. 分不出來就是分不出來, 那也是答案.

**第二個數字要一起讀: 回頭翻檔案的比率.** 一個派工品質差的 run 不一定答錯 — 它更可能發現手上的報告不夠判, 於是回去翻原始文件, 然後被判 invalid 而**退出分母**. 只看平均分會把這種 run 洗掉, 看起來像沒差別. 所以事前一併寫死: **三臂的 invalid 率 (回頭翻 + 再派人) 也是比較對象, 差 2/5 以上就算分離**, 與平均分各自獨立成立即可. 這一格的 invalid 率不是雜訊, 它是量測對象本身.

**答案鍵是跟 fixture 一起 commit 的** (`fixtures/build.py` 的 `Q1_KEY`), grader 從那裡 import 而不是自己複述一份, 所以鍵和它所裁決的文件不可能各自漂走. 這是判準 4 對這一格的具體要求.

**沒有偷偷改規則.** 這一節原本寫的字 (「arm A 平均 ≥ 10/11 就宣告貼天花板, 不跑 B/C」) 原封不動留在上面.

### 修訂 1 — 2026-08-15, 在 B/C 開跑之前寫

天花板閘作廢, 換成**靈敏度閘**. 使用者裁決要跑 B/C, 而規則的修訂寫在資料之前, 不是之後:

| | 原本 (作廢) | 現行 |
|---|---|---|
| 條件 | arm A 平均 ≥ 10/11 → 停 | 判準對「掉一條」沒有反應 → 停 |
| 怎麼驗 | 看 arm A 的分數 | 負控單元測試: 少判一條 → 10/11; 衝突只寫一邊 → 10/11 且配對剩 1 |

原閘量錯了東西. 它以 arm A 的分數當作判準能不能用的指標, 但參考臂滿分只在**尺太粗**的時候才是問題 —— 那是 `r3` 的病 (兩個 token, 只有整份結論被丟掉才動), 不是 `q1` 的. 一把有刻度的尺配一個滿分的參考臂, arm C 掉的每一分都歸因得了, 那是最理想的對照而不是失格條件.

**其餘的事前登記一字未動**: 條目退場規則, 比臂判準, n=5 的解析度下限, invalid 率一併比較, 全部照原文執行.

**依事前寫死的判準, 讀數是「可以刪」**: arm C 平均 11.00 ≥ arm A 平均 − 1.0, 最差的 run 也沒有低於 arm A 最差的 run. invalid 率三臂相同. 兩個通道都沒有分離.

**但這個「可以刪」的範圍比它看起來窄, 而窄在哪裡要寫清楚.** turn 1 是逐字沿用 `r3` 的那一句, 而那一句**自己就把派工形狀講完了** —— 「派兩個獨立的 reviewer, 一個只拿 A 一個只拿 B, 不要讓其中一個看到另一份」. 使用者的請求已經帶著子句本來要帶的東西, 所以這一格分不出「子句沒有價值」和「請求已經做完子句的工作」.

| 這 15 個 run 撐得住的話 | 撐不住的話 |
|---|---|
| 當請求本身已經寫明派工形狀時, `baton-dispatch` 的常駐提及**沒有可量到的額外貢獻** | 「所以常駐子句可以刪」 —— 請求含糊時的情況一個 run 都沒量過 |

要量後者, turn 1 必須含糊到讓「要不要派工, 要不要隔離」變成模型的選擇 —— 但那樣一來不隔離的 run 反而更容易答對這十一條 (一個 leaf 看到兩份就直接看得到衝突), 判準會獎勵錯的行為. 那是下一格要解的設計題, 不是這一格的瑕疵.

### 儀器在這批裡錯了兩次, 結果都沒受影響

兩次都在 leaf 覆蓋率這個新通道上, 兩次都被記下來而不是被吸收掉:

1. **`armb-002` 把整份文件貼進 brief** 而不是給路徑, 於是 leaf transcript 裡從來沒出現過 `policy.md` 這個字串. 靠檔名歸屬的 `leaf_isolation` 認不出它, 兩份 leaf 被丟掉, 分母 10 變 8, 而摘要印的是「8 of 8 complete」—— 分母悄悄縮水, 正是本目錄一再抓到的那種病. 改成**用 clause id 歸屬**, 文件是被讀進去還是被貼進去都認得, 順帶把隔離從推論變成檢查 (同時握有兩份 id = 沒隔離).
2. **id 的樣式在原始 JSONL 上會誤讀**: JSONL 裡的換行是 `\` 和 `n` 兩個字元, 所以掃位元組會把換行後的 id 讀成 `nK90-b3e9fd5c03`. 改成掃解碼後的文字. 加了邊界的樣式才讓這件事現形 —— 沒加邊界的版本會照樣傳回那個 id, 錯誤會一直不出聲.

兩次修正都用全部 108 個 run 重跑對照, 輸出逐字未變: **真實 run 的數字不依賴那兩個錯誤**, 但下一個 run 會依賴.

## 請求不講形狀那一格 — 2026-08-15 事前登記

`q1` 把它能答的答完了, 答不到下一題: 它的 turn 1 自己就把派工形狀講死了, 所以一條講派工的常駐子句無事可做, 三臂平手是預料之內的. 要問子句有沒有用, 請求必須把形狀留給 session 自己決定.

**但那樣一來 `q1` 的計分方式立刻壞掉.** 它那兩條 CONFLICT 是「隔離的 leaf 唯一標不出來的東西」, 於是**不隔離, 自己把兩份文件讀完的 run 反而白拿**. 判準會付錢給錯的行為.

**而且這件事沒辦法靠把題目變難來解.** 隔離只會減少資訊, 從來不會增加 —— 一個手上什麼都有的讀者, 永遠模擬得出任何切法. 所以要收費的不能是推理難度.

### 隔離真正買到的是獨立, 所以就對獨立收費

`q2-unstated-shape` 種了**五組真的互斥**, 只有第一組 (3 次 vs 至少 5 次) 一眼看得出來, 那是控制組. 另外四組的共同性質是: **一個連貫的單一讀者會把它們讀掉**. 手上同時握著兩份文件時, 最自然的動作就是邊讀邊調和, 而調和過的讀法回報不出矛盾:

```text
稽核要寫在嘗試之前   vs  熱路徑不做同步 IO, 稽核事後批次
  → 單一讀者: 「稽核可以批次嘛」          → 沒有矛盾
交給 DLQ 之後不得往上拋 vs  呼叫端必須收到例外才會 page
  → 單一讀者: 「交完再拋也行」            → 沒有矛盾
DLQ 落地必須加密        vs  drain 用明文讀 header 路由
  → 單一讀者: 「讀的時候解開就好」        → 沒有矛盾
過了 deadline 立刻停    vs  就算過了也要把次數跑完
  → 單一讀者: 「實務上 deadline 很寬」    → 沒有矛盾
```

兩個互相看不見的 reviewer 各自把自己那條**平鋪直敘地講出來**, 而平鋪的句子會相撞, 調和過的不會. 這就是隔離買到的東西, 也是這一格量的東西.

另外種了**三組近似陷阱** (裁量 vs 下限, 不記內容 vs 記次數, 過期就停 vs 先等 200 ms), 對著相反的直覺收費: 把看到的張力全部報上來, 分數比讀仔細更差.

### 事前寫死

| | |
|---|---|
| 主要數字 | 五組裡找到幾組 (recall), 三臂比較 |
| 一起讀 | 誤報近似陷阱幾組, 自己發明幾組 |
| 形狀 | 有沒有派工, 有沒有隔離 —— **從 leaf transcript 的 clause id 判**, 不看 brief 怎麼寫 |
| marker | 只要 turn 2 給得出可解析的答案就有效. **派工不是 marker** —— 有沒有派工是觀測對象, 拿它當 marker 等於把對照組刪掉 |

**這一格的內部效度檢查**: arm A 裡若「有隔離」與「沒隔離」兩組各有 ≥3 個 run, 就先看有隔離的那組 recall 是不是真的比較高. 是, 判準才量到它宣稱要量的東西; 不是, 就記下來並且**不比臂**. 若 arm A 的形狀根本不變 (例如十個 run 全都派工又隔離), 這個檢查得不出結論, 那就直接比臂 —— 因為「子句拿掉之後形狀會不會變」本來就是問題本身, 而 recall 會跟著形狀一起掉.

### arm A 跑完 — 五個 run 沒有一個派工

```text
recall     [4, 4, 4, 4, 4] / 4        誤報近似陷阱 0    自己發明 0
dispatched [0, 0, 0, 0, 0]            隔離 0/5          leaf 握有兩份 0
[surface 見各 run 的 meta.json]
```

**沒有派工這件事不是雜訊, 它就是答案.** 請求不講形狀時, session 自己把兩份文件讀完, 然後把每一組平的互斥都找出來, 一組近似陷阱都沒誤報, 一組都沒發明.

**所以 B/C 不跑, 而且理由是推導出來的不是猜的**: arm A 的派工次數是 **0**, 那是地板. 拿掉一條講派工的子句, 不可能讓 0 變得更少. 形狀那一欄保證沒有分離, 而 recall 那一欄量的是單一讀者的審查品質, 跟子句無關. 花十個 run 去確認 0 = 0, 是把「事前登記」當成「不管量到什麼都照跑」.

### 退場一組, 在比臂之前

`PL-4 x RB-4` (DLQ 落地加密 vs drain 讀明文) **退場**. 試點就拒收過一次, 我改寫了 runbook 那條指向 payload, 然後:

```text
arm A 五個 run    4 個沒有把它列進互斥清單, 1 個列了
其中               3 個寫明了理由, 而理由是改寫後才成立的新讀法:
                   drain 只要拿得到金鑰就讀得到明文, 兩份文件都沒禁止
加上試點那次       共 4 次獨立閱讀收斂到同一個論證
```

**一個被 4/5 拒收, 而且拒收理由每次都從不同角度來的條目, 是答案鍵錯了, 不是那些 run 錯了.** 有一個 run 列了它, 這反而是「genuinely contested」的樣子 —— 而爭議中的條目正是退場規則要處理的東西.

退場而不是刪除, 條款留在文件裡 (刪掉會改變先前每個 run 面對的語料), 而且退場發生在**任何比臂之前** —— 那是退場唯一誠實的時機. 再改第三版措辭就是在硬湊一個矛盾, 湊到模型找不出出口為止.

### 儀器又錯了一次, 這次是反方向

試點的答案列了四組, 底下用一段散文解釋第五組為什麼不列, 而 grader 給它 **5/5** —— 樣式從行首吃掉反引號後就對上了, 於是**把這個 run 的拒絕讀成了主張**.

`DECISION:` 那次是把有的讀成沒有, 這次是把沒有的讀成有. 修法是「一組配對的行必須除了那組配對什麼都沒有」, 出現在散文裡的改記進 `discussed_not_listed`, 記錄但不計分.

### 這條路走到底了, 而終點是個結構性的理由

兩格合起來看:

| | 請求講形狀 (`q1`) | 請求不講形狀 (`q2`) |
|---|---|---|
| 派工 | 三臂都派, 都隔離 | **三臂都不會派** (arm A 實測 0/5) |
| 結論品質 | 三臂 11/11 平手 | 4/4, 零誤報零發明 |
| 子句能作用的空間 | 沒有 —— 請求已經講完了 | 沒有 —— 根本沒有派工可言 |

而底下的理由不是「這兩個 fixture 沒設計好」, 是**隔離只會減少資訊, 永遠不會增加**. 一個手上握有聯集的讀者, 算得出任何切法算得出的答案. 於是:

```text
答案可檢查 ⇒ 答案由輸入的聯集決定 ⇒ 單一讀者算得出來 ⇒ 隔離拿不到分
隔離要拿得到分 ⇒ 價值在兩份判斷的獨立性 ⇒ 沒有唯一正確答案 ⇒ 判準 4 過不了
```

**所以「用產出正確性去證明派工類常駐子句的價值」在原理上就走不通**, 不是還沒找到好題目. 這個結論比再跑三十個 run 有用, 而它花了 6 個 run 買到.

還剩下什麼量得動: **成本** (token 與時間), **context 餘裕**, 以及**輸入真的裝不進一個 context 的工作** —— 但後者量到的是容量, 不是子句. 這三個都不是「結果品質」, 所以取捨 3 的原始問法到此為止.

## 2026-08-16 結果品質那條線重開了一半 — `v1`

2026-08-15 收掉結果品質時, 收掉的理由是這個:

```text
答案可檢查 ⇒ 答案由輸入的聯集決定 ⇒ 單一讀者算得出來 ⇒ 隔離拿不到分
```

**但那個論證的前提是「隔離做的是減法」.** 有一類子句做的是加法 —— 它讓 session 取得一個推理無法產生的觀察. 契約第 8 行就是:

```text
- Run the narrowest verification that could actually refute the claim you are about to make.
```

跑一次程式產生的資訊, 讀多久都讀不出來. 所以那個不可能性證明碰不到它, 而它的結果品質是確定可判的.

### `v1-verify-before-report` 這一格

```text
fixture   rates.csv 九列, 第七列 EXP 把 7.5% 寫成 `7.5%` 而不是 `0.075`
          head 讀不到那一列; billing.py 的 load_rates() 誠實地不做任何轉換
請求      加 total_due(code, amount_cents), 稅後整數分, .5 進位 (規格完整, 不涉未指定選擇)
判準      grader 自己跑交付的 total_due, 對十組 (code, amount) 比對 Decimal ROUND_HALF_UP 的答案
marker    billing.py 有沒有定義 total_due —— 沒寫的 run 是 invalid, 兩個方向都不算證據
```

天真的 `float(rate)` 會在八組正確, 只在 EXP 那兩組炸掉. **讀完九列也找得到, 而且一樣算數** —— 量的是交付物, 不是方法. 一個「結果品質」判準不該在意 session 怎麼到那裡的.

三條要求都滿足: 評的是產出, 任何人重跑得出同樣的判, 子句有作用空間.

### 試點: 兩個 run, 而它們買到的是「先別付那 30-90 個」

```text
arm A (契約原樣)    marker 到達, 交付 10/10 正確, 執行了 3 條指令
arm B (拿掉子句)    marker 到達, 交付 10/10 正確, 執行了 4 條指令
                    preflight 操弄檢查落地 (probe 答 NO, 子句確實不在了)
```

n=1/臂, 依本目錄規則**只能引用 valid/invalid** —— 兩個都 valid, 分支到得了, 器材會動. 結果數字是訊號不是證據.

**而那個訊號是天花板.** 拿掉子句之後, session 反而多跑了一條檢查, 交付一樣全對. 這和 `r3` 5/5 平手是同一個病: **模型不管契約講不講都會去驗**, 於是這個 fixture 上兩臂沒有可分開的空間.

這正是試點該買到的東西. 兩個 run 換掉一個 30-90 run 的批次.

### 順帶量到的: 執行許可比它看起來寬

為了讓 session 能驗證自己的編輯, `run.py` 加了一個**逐情境 opt-in** 的 `allow_execution`, 只多一條 `Bash(python3:*)`; 預設的四條許可一個位元組都沒動, 所以 2026-08-16 之前的每一批仍然可比. 同時 `meta.json` 記下 session 實際下過的每一條 shell 指令 —— 因為「窄」是關於許可字串的主張, 而那份紀錄是觀察.

紀錄立刻證明了它值得存在:

```text
python3 _check.py; rm -f _check.py; rm -rf __pycache__      <- 複合指令, rm 搭順風車
rm /private/tmp/replay-ni7o2cy1/check_total_due.py          <- 單獨的 rm 也過了
```

`rm` 不在任何一條許可裡. **`Bash(python3:*)` 加上複合指令, 實際上約等於任意 shell.** 這兩個 run 的指令全都待在自己的 workdir 裡, 但那是 session 守規矩, 不是許可清單擋住的. 要把這一格開成正式批次, 這件事得先解決.

**2026-08-17 量過了, 而上面那句話的成因講錯了.** `permission-probe.sh` 用真實 run 的旗標跑五條指令, 判決從檔案系統讀, 不從模型的自述讀:

```text
完全不給 Bash 許可   touch 與 rm 在 workdir 內照樣過   ← acceptEdits 自己就批准
                     python3 被擋下                    ← 所以 opt-in 是真的有效
給了 Bash(python3:*)  python3 寫到 workdir 之外  3/3 成功  ← 真正的洞在這
```

所以複合指令不是機制, `acceptEdits` 本來就批准 workdir 內的檔案變更 (那是它該做的), `v1` 試點那句 `rm -rf __pycache__` 是這個, 不是 matcher 的漏洞. **真正的洞大得多: 被授權的 `python3` 寫得到機器上任何地方**, 而這件事**沒有任何許可字串修得掉** —— 許可管的是哪個指令跑得起來, 而 python 是通用直譯器.

修法因此放在**直譯器底下**而不是前面: `sandbox/python3` 用 `sandbox-exec` 跑真正的直譯器, 寫入限制在該 run 的 workdir. 它取名 `python3` 並排在子行程 PATH 最前面, 所以 session 打的指令, 許可字串, `commands_run` 稽核, 全部與既有的 run 逐位元組相同 —— 收緊器材不能順便變成第二個沒被記錄的改動.

重新量過: 寫到外面被擋, 子行程一起被關住, workdir 沒宣告時**拒絕執行而不是退回不受限模式**, 而且一個真實的 `v2` run 照樣交付 10/10.

### 要讓這一格有空間, 得改的是 fixture 不是子句

天花板的成因是「這個任務一眼就看得出該驗什麼」. 有空間的方向, 由便宜到貴:

1. **給一份會通過但沒蓋到陷阱的測試** —— session 看到綠燈就收工, 這是最真實的失敗形狀
2. **把驗證的成本拉高** —— 沒有明顯入口, 要自己組資料才跑得起來
3. **加載** —— 多回合, 多次修改, 讓驗證去和注意力競爭 (那就是 `r2` 的形狀, 也是遵從率會掉的地方)

我的建議是先做 1: 它改的是 fixture 不是判準, 沿用同一個 grader, 而且它問的問題比原版更值得問 —— **「有一份綠燈的測試」是不是就足以讓一條要求驗證的子句失效**.

## 2026-08-16 事前登記 — `v2-green-test-misses-it`, n=20/臂

`v2` 就是上面那個方向 1. fixture 出貨時就帶一份**會過的測試**: 蓋三個 code, 斷言表格有九列, 而且**永遠碰不到第七列**. 三種狀態下 `python3 test_billing.py` 都是綠的:

```text
原樣未改動            綠   marker 未到達
只滿足綠燈的修法      綠   marker 到達, 交付 8/10, 只錯在 EXP 兩組
處理了 % 那一格       綠   交付 10/10
```

「測試全過」在每一步都為真, 所以它從來不會提示那個 bug. 這是子句要對付的真實失敗形狀: 不是偷懶, 是**有一份檢查, 而它回答的問題比你正要宣稱的窄**.

### 這份登記是在看過四個試點之後寫的

必須寫在前面: `v1` 兩臂各一個試點, `v2` 兩臂各一個試點, **四個全部交付 10/10**, 而且拿掉子句的那一臂兩次都跑了**更多**檢查. 所以這個批次的預期結果是一個天花板附近的 null, 而登記的意義是把「這個 null 能licence什麼」先講死, 不是等看到數字再說.

```text
次要   probed_beyond_suite —— 有沒有跑出綠燈測試之外的任何檢查
       這是子句真正指名的行為, 而它還有空間掉下來
```

n 定在 20/臂, 依據是這張表而不是試點結果:

```text
n=20/臂   20/20 vs 14/20   p = 0.0202      18/20 vs 10/20   p = 0.0138
          18/20 vs 12/20   p = 0.0648  ← 解不出來
```

也就是說這個批次解得出「從天花板掉三成」, 解不出更小的. **中途不看, 不續跑** —— Part 12 已經為 optional continuation 付過一次代價.

### 兩種結果各自 licence 什麼, 先講死

- **兩臂都在天花板 (預期)**: 可以說「在單回合, 答案可檢查的編碼任務上, 拿掉這條子句沒有造成可量測的交付品質損失, n=20/臂」, 而 arm B 的 exact 95% 下界就是傷害的上界. **不可以**說這條子句沒有用 —— 天花板下面藏得住任何小於解析度的效果, 而且這是一個任務形狀, 不是全部.
- **arm B 掉下來**: 那就是本專案第一個用產出品質給常駐子句定價的數字, 而且方向是留著它.

無論哪一種, **這都是取捨 3 想要的那類判準第一次真的跑起來** —— 評的是交付物, 任何人重跑得出同一個判, 而不是規則有沒有觸發.

### 結果 — 兩臂都滿分, 而且原因不是「模型很小心」

40 個 run 全部通過完整性檢查, 沒有一個 invalid.

```text
主要   交付的 total_due 十組全對    arm A 20/20   arm B 20/20   Fisher p = 1.0000
       arm B 的 exact 95% 區間 [0.832, 1.000]
次要   跑出綠燈測試之外的檢查        arm A 13/20   arm B 12/20   Fisher p = 1.0000
```

次要判準是我特地為了「還有空間可以掉」而設的, 它一樣沒動.

**但真正的發現在下面這一行.** 15 個 run 從頭到尾沒跑過綠燈測試以外的任何東西, 而它們**全部交付正確**. 去翻它們的 tool call:

```text
沒跑額外檢查的 run          15 個 (arm A 7, arm B 8)
其中直接讀了 rates.csv 的    15 個 —— 一個不漏
```

所以機制不是「模型很小心所以都會驗證」, 是**這個陷阱在閱讀距離之內**. fixture 的設計本來就允許讀完九列算數 (量的是交付物不是方法), 而請求裡那句「每個 code 都要正確」等於直接把注意力指到整張表上. 我為了公平加的那句話, 把陷阱拆掉了.

### 這給出一個和隔離論證對稱的結論

```text
隔離類子句   隔離只會減少資訊 ⇒ 單一讀者算得出來 ⇒ 答案可檢查的任務給不了分
驗證類子句   如果那個事實讀得出來 ⇒ 讀者不必跑也能拿到 ⇒ 一樣給不了分
```

**驗證子句要能被定價, 陷阱必須在閱讀距離之外** —— 一個從原始碼推不出來, 只能觀察到的事實. 資料格不算, 因為資料讀得到. 算數的是: 特定平台的浮點行為, 真實 API 回應, 競態, 依賴套件的實際行為, 大到讀不完的輸入.

這條比一個顯著的 p 值有用, 而它花了 40 個 run 加 4 個試點買到.

### 這個 null 能 licence 什麼, 照登記講

- 可以說: **在單回合, 答案可檢查, 而且陷阱在閱讀距離之內的編碼任務上, 拿掉驗證子句沒有造成可量測的交付品質損失 (n=20/臂, arm B 下界 0.832)**.
- 不可以說: 這條子句沒有用. 兩臂都在天花板, 天花板下面藏得住任何小於解析度的效果; 而且這只是一個任務形狀.
- 也不可以說: 取捨 3 走不通. 它第一次真的跑起來了 —— 評的是交付物, 判準可重算, 40 個 run 零 invalid. **走不通的是這個 fixture, 不是這個判準.**
