# Loop engineering: 單一 agent 的迴路

**規劃 → 執行 → 驗證 → 重試.** 這一層問的是一個 agent 拿到一件事之後怎麼收斂: 走幾圈,
每圈檢查什麼, 什麼時候停, 以及停不下來時交給誰.

它包住 [harness](harness-engineering.md): 權限決定每一圈能做什麼, 迴路決定要走幾圈.

**管什麼.** 從一個請求到一個可驗收結果之間的迴路: 走幾圈, 每圈檢查什麼, 什麼時候停.

**怎麼做.** 總原則是**[最短驗證迴路優先](../engineering-playbook.md#3-四個原則)** —— 秒級檢查前移到 hook, 中等成本由 agent 明確
執行, 慢速或主觀的驗收由人做而 agent 供證據. 收斂靠兩個明寫的上限: 同一個 readiness-unit
最多兩次自動實質修訂, 之後把選項交還使用者; 同一個目標最多五次重驗, 而且每一次都要先講
出上一次之後改了什麼, 沒改的候選不重驗.

**用什麼量.** 多回合 replay 的四項存活判準: 活著結束, 到達受測邊界, 派工有紀錄, 可獨立
重算. 前兩項閘判決, 第三項只回報.

**已知怎麼壞.**

- **「沒發生」最容易假造.** replay 量的絕大部分是「沒有重複寫入」「沒有失控疊加」這類
  否定句, 而一個什麼都沒做的 run 在每一格都滿分. 存活判準就是為這件事**先於開跑**寫的,
  順序是刻意的.
- **判準寫成閘, 程式卻只當回報.** 文件說四項全過才算數, 而 grader 從第一天起只用前兩項
  閘判決. 這個矛盾到 2026-08-15 才被查出來, 而在那之前每一列被引用的結果, 第三項都大多
  不合格.
- **零結果不等於沒效果.** 需要一組反向對照才分得出「這條規則沒用」與「這把尺量不到」.

**要動它得先拿出什麼.** 改迴路長度或修訂上限要 replay 證據, 而且判準要先寫再開跑 ——
先跑再補判準, 等於先製造一批要靠人記得去質疑的結論.

## 四個階段各自的停止條件

| 階段 | 這個 repo 的做法 | 停不下來時 |
|---|---|---|
| 規劃 | Plan 交 `plan-verifier` 要 `READY` 或 `REVISE` | 同一個 readiness-unit 兩次自動實質修訂後交還使用者 |
| 執行 | 一個可寫 artifact 一個 owner | 越界就是 QC 的事, 不是靠 agent 自律 |
| 驗證 | 最短迴路優先; outcome verifier 至多一個, 放在最小完整驗收邊界 | 同一目標五次重驗上限, 到頂就攤開未解發現 |
| 重試 | 每次都要先講出上一次之後改了什麼 | 沒改的候選不重驗 |

## 還沒貼合的部分

- **重試的證據最薄.** 五次上限來自 ledger 裡一條 2026-07-28 的四次鏈, n=1.
- **「規劃」在單 agent 迴路與多 agent 拓撲之間跨界.** Plan 收斂寫在派工 skill 裡, 因為
  實務上它總是與派工一起發生; 這是實作先於分類的一處, 尚未收斂.
