# Context engineering: 模型看到什麼

四層裡最內層. 它決定的是**這一回合模型眼前有什麼**, 而其他三層都建立在這個答案上:
工具再多, 迴路再嚴, 拓撲再漂亮, 模型看不到的東西就等於不存在.

這一層有兩個尺度: 一條子句怎麼寫, 以及整個 window 裡放什麼. 前者是這個 repo 量得最細的
地方, 後者是花費最大的地方.

## 一條子句

**管什麼.** 單一一條規則的措辭與位置. 這是本 repo 量得最細的一層, 因為它是唯一能做
A/B 的粒度.

**怎麼做.** 什麼配得上常駐, 由 [playbook 第 1 節](../engineering-playbook.md#1-核心立場)
的四類與那句判準決定 —— **刪掉這一行會不會犯錯? 不會就刪.** 本 repo 在那之上加的是量:
兩份契約各有字數上限, 外加三項密度指標 (規則條數, 每條的位元組數, 廢話比例), 所以
「把一句話寫長」換不到更多規則. 每支 skill 與 role 的 `description` 各有自己的上限,
規範在[契約瘦身](../contract-slimming.md).

**用什麼量.** [prompt-surface-census.py](../../scripts/prompt-surface-census.py) 說哪一句
在哪一層, 各多重; [contract-operator-delta.py](../../scripts/contract-operator-delta.py) 在
壓縮契約時逐個連接詞, 範圍限定詞與否定詞對照, 因為那三類改動不會動到任何被斷言的短語,
測試綠燈不構成證據.

**已知怎麼壞.**

- **規則存在不等於規則生效.** 字串測試只證明那句話在檔案裡. 上游有過一次紀錄: 255 條
  短語斷言全數通過, 而同一份檔案裡放了十二個語意缺陷.
- **搬家其實是漲價.** 把一句話從 skill 本文搬進 `description`, 它就從「按需載入」變成
  「每回合都在」.
- **矛盾更貴.** 論證在 [playbook 第 1 節](../engineering-playbook.md#1-核心立場);
  對這一層的意思是, 牴觸供應商 system prompt 的子句是 bug, 處置是刪那一行, 不是加字解釋.

**要動它得先拿出什麼.** 改措辭要事前登記的本機 A/B —— 這一層的效果量大到三倍, 也小到
點估計翻倍還過不了事前門檻, 兩種都發生過. 新增子句要先證明「刪掉它模型會犯錯」, 再做
預算換算.

## 一個 window

**管什麼.** 一次 session 的 context 由什麼組成, 什麼時候載入, 什麼時候收回.

**怎麼做.** 三個付費點 (見[軸一](architecture.md#軸一-在哪裡付費)) 就是這一層的骨架. 之上是漸進揭露:
`SKILL.md` 只放路由與主流程, 深度資料放 `references/`, 讓需要的人再付第二段. 大型唯讀
輸入走壓縮而不是塞進 window. 長任務在收斂點分段, 而不是靠固定的百分比失效線.

**用什麼量.** [resident-pool-report.py](../../scripts/resident-pool-report.py) 量這台機器
實際扛多少常駐 skill 描述, 並且分成本 repo 管的, 專案的, 沒人管的三份;
[docs-size-report.py](../../scripts/docs-size-report.py) 量拉取層, 分現行指引與紀錄兩層.

**已知怎麼壞.**

- **預算蓋到的比想像中少.** 常駐 skill 描述的預算蓋不到 CLI 內建與 plugin 的 skill, 所以
  `resident-pool-report.py` 報出來的是**下界**, 不是總數. 它自己在輸出裡說這件事.
- **靜態負載不是大頭.** 真正吃掉 window 的是動態流入 —— 大輸出, 探索 dump, 貼進來的
  日誌. 修剪常駐是必要的, 但它不是這一層最大的槓桿.
- **兩端不是同一張表.** 同一支 skill 在 Claude 與 Codex 的付費點不同, 拿一端的數字談
  另一端會高估.

**要動它得先拿出什麼.** 動常駐要換算預算, 而且是三項密度指標一起看. 拉取層沒有字數
預算, 只有一道數量級鬆閘, 逼近它的正解是拆檔或搬回真正的 owner, 不是調高常數.

## 跨回合與跨 session

前兩節講的是**這一回合**看得到什麼. 一個 window 會被壓縮, 一個工作階段會結束, 而下一次
開始時模型什麼都不記得 —— 所以這一層還有第三個尺度: **什麼東西活得比一個 window 久.**

三種持久化, 三個不同的擁有者, 不可互相代換:

| 放什麼 | 存在哪 | 誰擁有 | 活多久 |
|---|---|---|---|
| 可攜契約, 角色, skill | Git, 經部署到 HOME | 這個 repo | 直到有人改它 |
| 派工結果與 route 證據 | machine-local ledger | 機器 | 累積, 只追加 |
| 跨 session 的個人事實與專案約束 | CLI 自動記憶 | 使用者 | 直到被更正或刪除 |

分層的判準在 [playbook 的落點表](../engineering-playbook.md#2-文件與機制分工): 記憶只放
**repo 沒有記錄的東西** —— 結構, 歷史, 契約內容都已經在 Git 裡, 再抄一份到記憶只會多一份
會漂移的拷貝.

### 壓縮邊界只能事後補, 不能事前塑形

一個很自然的想法是「壓縮之前先把目標與未決項保住」. **做不到**, 而理由是機制層面的:
`PreCompact` 只能否決壓縮或做副作用, 不能加進或引導摘要保留什麼 (2026-07 對著 hooks
reference 驗過).

所以這件事只能做成**壓縮之後的重播**: `SessionStart` 會在壓縮完成後再次觸發, `source` 是
`compact`, 而它是少數 `additionalContext` 會被注入的事件.
[`compact-reseed.py`](../../main/claude/hooks/compact-reseed.py) 就掛在那裡, 在那個邊界
確定性地送一次提醒, 把「希望摘要有留住」換成「不論摘要留了什麼都會再說一次」.

推論下去有一條規則: **關鍵規則不能靠壓縮存活.** 常駐契約在壓縮碰不到的層 (它隨每一回合
一起送), 而寫在對話裡的約定只要跨過一次壓縮就可能不見. 這也是為什麼「這一條該不該進契約」
的判準不是重要性, 是「它需不需要活過壓縮」.

### 外部怎麼做, 以及這裡差在哪

跨 session 的主流做法是**結構化筆記**: 維護一份目標, 決策, 下一步與未決問題的狀態檔, 下次
開始時讀它而不是重播 transcript. 本專案兩件都在跑 —— 記憶目錄是一事一檔加一份索引, 壓縮
邊界有重播 —— 所以這一格不是缺口, 是已經收斂到同一個答案 (見
[peer-harnesses](../research/peer-harnesses.md#langchain-deep-agents)).

真正還沒有的是**觸發策略的知情權**: 壓縮什麼時候發生由 client 決定, 這裡既不控制也量不到,
所以「這次壓縮掉了什麼」只能靠壓縮後的重播兜底, 而不是靠事前判斷值不值得壓.

## 窗口實際被什麼填滿 (2026-08-21 量的)

前面三節講的是**應該怎麼分配**. 這一節是這台機器上 26 個真實工作階段實際發生的事,
由 [`context-inflow-report.py`](../../scripts/context-inflow-report.py) 產出.

先看不含估算的兩個數字, 它們直接來自每次請求回報的 `usage`. **這是 2026-08-21 一次的
觀察, 不是常數** —— transcript 語料每天在動, 同一天稍晚重跑就變成 23 個階段與 12.1%.
承重的是量級 (常駐大約是尖峰的八分之一到七分之一), 不是小數點:

| | 中位數 |
|---|---|
| 常駐內容 + 開場那一句 | 40,495 tokens |
| 那個工作階段見過的最大窗口 | 232,200 tokens |
| 常駐佔最大窗口 | **14.7%** |

**這一層有預算, 有守衛, 有三支報告腳本盯著的, 是那 15%.** 剩下的 85% 一直沒有任何儀器.
把小的那一半守到個位數字, 大的那一半連基線都沒有, 看起來像紀律, 其實是把尺放錯地方.

剩下那 85% 的組成只能估算 —— transcript 不等於 prompt, 而重估出來的量比實際成長少了
約 1.84 倍, 且倍率在不同工作階段之間從 0.29 到 3.80 都有. 所以下面**要當排序讀, 不要
當百分比讀**, 而報告本身每次都把這個倍率印出來:

1. **工具結果**最大, 其中 Bash 約六成, Read 約三成.
2. **模型自己的工具呼叫參數**次之, 其中 Bash 過半, 其次是 Edit 與 Write —— 也就是說
   「寫檔」這件事在請求端和回應端各付一次.
3. **注入內容**第三, 來自 skill 清單, hook 回覆, 檔案差異這類每回合被塞進來的東西.
4. 模型回覆文字, 使用者訊息與 thinking 加起來是尾數.

推論下去有一條會改決策的: **常駐字數預算不是省 context 的主要工具, 它是保證關鍵規則
一定在場的工具.** 兩者的理由不同, 而先前那條落差把它們混在一起了 —— 見
[playbook 第 1 節](../engineering-playbook.md#1-核心立場).

## 還沒貼合的部分

- **流入的組成只有排序, 沒有精確值 —— 但已經知道錯在哪一側.** 2026-08-21 查了那個 1.84
  倍: **token 曲線是準的, 低估的是字元估算**. 一個 200k 的工作階段六次壓縮, 壓縮前的峰值
  是 165,746 / 162,450 / 166,939 / 166,569 / 166,538 —— 五個值落在 4,500 之內, 正好是自動
  壓縮的觸發點. 一個會系統性高估的量測不會這樣收斂.
  單回合的差分另有假影: 有一次請求窗口跳了 23,594 token 而 transcript 只記了 4,592 個
  字元, 而它的 usage 顯示 `cache_read` 從 0 變成 28,992 且 `cache_creation` 仍有
  33,848 —— 快取重新分段時同一段會同時落進兩個桶子. 那解釋了倍率為什麼在 0.29 到 3.80
  之間跳, 不解釋中位數為什麼是 1.84.
  **要分開那兩者需要對真正送出去的 payload 數 token, 而 transcript 裡沒有那個東西.**
  所以佔比仍然只能當排序讀.
- **子句的效果只在兩條規則上量過.** 措辭 A/B 覆蓋語言子句與派工子句, 其餘子句的效果
  是外推的.
- **壓縮發生時機量不到.** 觸發由 client 決定, 而這裡沒有任何紀錄說「這次壓縮掉了什麼」;
  重播是兜底, 不是觀測.
- **記憶的時效檢查只看指涉, 不看內容.**
  [`memory-freshness-report.py`](../../scripts/memory-freshness-report.py) 會抓路徑失效,
  連結斷掉與索引不同步, 但一條記憶的**說法**本身過期時, 它指的檔案通常還在, 那種漂移
  沒有機械化的抓法.
