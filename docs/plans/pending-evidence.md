## 三之四, 舊 cache 讀數的污染查核 (2026-08-31)

**結論: 2026-08-31 11:04 之前的 cache 讀數一律不得直接重用, 而且無法逐筆分辨哪些真的受
影響.**

查了什麼:

```text
帳本帶 cache 欄位的列    109 / 164, 期間 2026-07-22 -> 2026-08-31
批次當天 (08-28) 的 proxy 流量   opus-5 208 筆, sonnet-5 153 筆
當時的 Headroom 版本      0.36.5 (#2085 的修正在 0.37.0, 本機 08-31 11:04 才升上去)
升上 0.37.0 之後的乾淨列   20 筆 (全部 executor)
```

所以批次**確實經由 proxy**, 而且是帶著那個缺陷的版本. `#2085` 的機制是平行 subagent 共用
fallback session id, 使凍結前綴逐輪位元組不穩, 於是**該被讀取的快取變成重寫** —— 方向上
會**壓低 cache_read 並抬高 cache_write**.

**真正的問題不是污染程度, 是分不出來**: 帳本沒有任何欄位記錄一筆讀數有沒有經過壓縮 proxy.
所以沒有一筆舊資料能被歸類為乾淨或受污染, 也就沒有辦法只修受影響的那些. 這是成本儀器那一
項要補的第一個欄位, 而不是一個統計問題.

**行為類結果不受影響**: trap 批次的 INTENT/TWINS 合規率是從報告正文評分來的, 不是成本量測.
10/10, 8/10, 9/10 那些讀數照舊成立.

### 順帶查出一個對不上的數字

`model-evidence` 的「leaf context window 實測」用兩個 ledger 讀數支撐「目前不需要把
`explore` 搬上 1M」: 我方 `explore` 中位 cache_read **4.3 KB**, 內建 `Explore` **168 KB**.
當場複算:

```text
explore   n=23   中位 4,348      期間 2026-07-30 -> 08-06     ← 對得上 4.3 KB
Explore   n=18   中位 449,642    全部在 2026-07-22            ← 對不上 168 KB
                 平均 1,616,281  範圍 38,400 - 16,949,168
```

**前者重現, 後者不重現**, 而且不是差一點: 中位是宣稱值的 2.7 倍, 平均是 9.6 倍, 十八個值
裡沒有任何一個接近 168,000. `Explore` 那 18 筆全部在 2026-07-22, 而該節寫於 08-06, 所以
不是「當時資料比較少」——寫的時候這 18 筆就都在了.

**沒有下結論說它錯**, 因為可能有一個我重建不出來的篩選條件. 但那個比較正是「不需要搬」的
唯一支撐, 所以在複算得出同一個數字之前, 該結論**只剩一半證據**.

## 三之六, 成本儀器剩下的接線: 卡在歸因, 不是計算 (2026-08-31)

[landing-readiness](../research/landing-readiness.md) 的建議四寫「缺的不是框架也不是欄位
定義, 是接線」. 接的時候發現那句話只對了一半 —— **框架是完整的, 但它餓的是輸入, 而輸入
拿不到**.

**框架這一側確實齊全**: `experience-report` 每個 cohort 已經在算 `avg_api_cost_usd`,
`avg_tokens_out`, `avg_total_tokens`, `avg_total_secs`, 而 `expected_total_cost` 的口徑寫在
`model-evidence`. 沒有東西要新建.

**輸入這一側**, 164 筆帳本實測:

```text
api_cost_usd     1/164     ← 幾乎沒有
review_secs      3/164
rework_secs      0/164     ← 從來沒有
tokens_in/out  109/164
token_scope full 90/164
```

所以 `expected_total_cost` 的**人力時間項是空的, 金額項只有一列**. 報告算得出
`avg_total_secs` 的條件是三個時間欄都在, 而 `rework_secs` 從來沒有 —— 那個平均永遠不會出現.

### 兩條看起來可以自動化的路, 都不能走

**一, 從 stub 自動導出 `review_secs`.** pending stub 有 `SubagentStop` 的 `ts`, 記錄時
`now - ts` 就是一個數字. 不做, 因為那個間隔常被「還沒有人記」主導而不是被審查主導 ——
當場的證據: 帳本旁那 23 筆 pending stub 是 **2026-08-28** 的, 擱了三天. 對批次尤其壞:
批次通常一次記完, 於是每一筆都會拿到同一個膨脹值.

只在間隔夠小時才導出也不行 —— 那會讓平均只蓋到「很快被記」的那些派工, 系統性低估審查
時間. 一個有選擇偏誤的數字比空欄位糟, 因為空欄位不會被平均進去.

**二, 從 proxy log 取實際成本.** 歸因**部分**可行, 而卡點很具體:

```text
帳本有 session 欄位的列              115/164
該 session id 在 proxy.log 出現       1,838 次   ← 歸因是做得到的
但出現在 event=proxy_inbound_request 的 headers 裡
帶著 token 與成本數字的是 PERF 行
帶 session id 的 PERF 行              0
同時帶 inbound id 與 hr id 的行        0
```

**識別碼在一種行上, 數字在另一種行上, 而沒有任何一行同時帶兩者.** 用時間鄰近去接是啟發式
不是查表, 而一個會錯接的成本儀器正是今天檢討要防的東西.

### 什麼能解開它

- **上游那側**: Headroom 支援 `x-headroom-session-id` 標頭. 若批次跑用得到它, proxy 就能
  自己把成本歸到一次批次 —— 但那要控制 Claude Code 送出的標頭, 我方目前做不到.
- **我方那側**: 讓 PERF 行帶 session id, 是上游的改動, 不是我方的.

| 項目 | 下一步 | 通過條件 |
|---|---|---|
| 成本歸因 | 查 Headroom 有沒有辦法讓 PERF 行帶 session id, 或讓 `/stats` 逐 session 分列 | 有: 接一支批次前後取差值的腳本; 沒有: 記「本 repo 量不到逐批成本」, 並停止在文件裡承諾成本數字 |
| `review_secs` / `rework_secs` | 不自動導出. 要嘛人工記, 要嘛承認這兩項永遠是空的 | 若三十天後仍是 0/N, 把 `avg_total_secs` 從報告移除 —— 一個永遠算不出來的欄位是雜訊 |

**已經做了的那一段**: `context_proxy` 欄位 (同日) 讓往後的每一筆知道自己有沒有經過壓縮,
那是歸因的前提, 而不是歸因本身.
